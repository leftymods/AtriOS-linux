# DTS review — mainline 7.3 / SM1

Scope: `mainline/dts/gen-ring-nodes.py` (generator) and the file it emits,
`mainline/dts/meson-sm1-yandex-station-max.dts`.  Reference tree: torvalds/linux
`master` as fetched on 2026-10-28 (`meson-sm1.dtsi`, `meson-g12-common.dtsi`,
`pinctrl-meson-g12a.c`, `dt-bindings/*`, `Documentation/devicetree/bindings/*`).

Vendor source of truth for every board-level value:
`AtriOS-linux/common/arch/arm64/boot/dts/amlogic/sm1_s905x3_yandex.dts`
(decompiled vendor DTB; periphs-bank GPIO numbers there are
`mainline index + 1`, because the 4.9 bindings header defines `GPIOV_0`, so
e.g. vendor `0x18 0x53` = `GPIOX_17`).

## 0. How this DTS is built, and how it was checked

The whole `.dts` is generated by `gen-ring-nodes.py` (HEADER + 72 LED nodes +
FOOTER); never edit the `.dts` by hand.  The generator now verifies its own
output (`verify()`): balanced braces, exactly 2 controllers, `reg = <1..36>` in
each, 36 children per controller, 72 labels
`station2:{red,green,blue}:ring1..24`, `max-brightness-scale = <200>`.

Compile check (real, not visual):

```sh
# mainline sources: meson-sm1.dtsi, meson-g12-common.dtsi,
# include/dt-bindings/{gpio,input,clock,reset,power,pwm,thermal,phy,leds,sound,...}
cpp -nostdinc -undef -D__DTS__ -x assembler-with-cpp -I. -Iinc \
    meson-sm1-yandex-station-max.dts -o pre.dts
dtc -I dts -O dtb -o out.dtb pre.dts      # dtc 1.7.2
```

Result: `cpp` clean, `dtc` clean.  The only warnings are the five that the
mainline SoC `.dtsi` itself emits with dtc 1.7.2 (`/soc/bus@ff600000/bus@34400/
pinctrl@40`, `/soc/bus@ff800000/pinctrl@14`, `/soc/bus@ffd00000/dsi@7000`) —
none comes from the board file.  `dtbs_check`/`dt-validate` was **not** run (it
needs the full kernel tree plus dtschema); the schema-level statements below
come from reading the matching bindings, not from automated validation.

Checks performed on the compiled blob: 72 `led@N` nodes inside `i2c@1f000`,
regs `1..36` in each controller, all aliases resolve to distinct nodes,
`phy-handle` resolves to `internal_ephy` (`ethernet-phy@8`, max-speed 100).

|---|---|---|---|
| SD controller | `&sd_emmc_b` `okay` | `status = "disabled"` (node kept) | `sdcard_cmd_c` and `i2c0_sda_c` are the **same pad**, GPIOC_5 (`pinctrl-meson-g12a.c` :160-165 vs :192-193), and `i2c0_sck_c` = GPIOC_6 takes the card-detect line (`gpio_cd`, vendor :3046). ## 4. Open items / risks (hardware verification or separate work)

1. **SPI and JTAG share the same pads.** `spi1_mosi/miso/clk/ss0` =
   GPIOH_4/5/7/6 (`pinctrl-meson-g12a.c` :186-189) and the panel asks for the
   same pins as `jtag-tdi/tdo/tck/tms`.  `spicc1_pins` keeps H_4/H_5/H_7 in the
   spi1 function and H_6 is owned by the SPI core as `cs-gpios`, so
   `gpiod_get()` in the panel driver returns `-EBUSY`.  This needs a pinctrl
   handoff (a `jtag` state on `spicc1` that the driver selects before
   reconfiguring the FPGA) — driver work; the DTS currently describes the
   hardware as it is.
2. **CS polarity.** Vendor `cs-gpios = <0x18 0x17 0x00>` is flag 0 (active
   high), but their driver toggled the line by hand.  The DTS keeps
   `GPIO_ACTIVE_LOW` (SPI norm): if the panel stays silent, check this first.
3. **eMMC VCCQ.** `vqmmc-supply = <&reg_1v8_d>` is inferred from
   `MMC_CAP2_HS200` plus the existence of the `1V8_D` rail (vendor :4374);
   that rail is not referenced anywhere in the vendor DT and both `1V8_D` /
   `3V3_D` are always-on.  If the schematic shows VCCQ = 3.3 V, drop
   `vqmmc-supply` and `mmc-hs200-1_8v`.
4. **`GPIOX_19` = BT host-wake** (vendor :3785, `0x55`) is not described
   (`host-wake-gpios`); the vendor DT does not encode a polarity (flag 0).
   Add it only after checking, otherwise false wakeups are possible.
5. **VDDCPU / cpufreq.** The vendor feeds the CPU through a `pwm-regulator`
   with a `voltage-table` (vendor :3168-3178, `vddcpu0`).  Mainline would need
   either `pwm-regulator` with `pwm-dutycycle-range` or a new binding that
   carries the table; guessing is not acceptable (wrong voltage = hangs or
   damage), so `cpu-supply` is left out and cpufreq stays disabled — the SoC
   runs at the bootloader frequency.
6. **SD slot** cannot work together with the ring (§2).  If the ring ever moves
   to another bus/pins, `&sd_emmc_b` is ready: `status = "okay"` plus
   `cd-gpios = <&gpio GPIOC_6 GPIO_ACTIVE_LOW>`.
7. **Wi-Fi (SDIO)** `&sd_emmc_a` is not enabled (planned last).  It will need
   `power_on_pin = GPIOX_6`, `interrupt_pin = GPIOX_7` (vendor :3792-3794),
   `mmc-pwrseq` and `non-removable`.
8. **HDMI / USB / audio** are not described here (audio: es7210 0x40,
   es8156 0x08, sy6045s 0x2a/0x2b on i2c1 — vendor :2085-2130).
9. `dtbs_check` has not been run (§0); it must be run on a full kernel tree
   before an upstream submission.

Exactly one of the two models may be in the tree — if the owner picks `atrios-keypad`, the `gpio-keys` node must go (otherwise both sides fight over the two pins with `-EBUSY`) |
